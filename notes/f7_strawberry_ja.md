# F7 イチゴの映像でカメラ対エンコーダの比 r を測る（Tue Oct 13 00:28:03 CST 2026）
問い：着地の後、手首カメラに映るパッドの移動は、エンコーダが予測する移動の何倍か（r）。コードは sim_demos/floor/strawberry_ratio.py、図は floor/strawberry_ratio.png（v2）。
v1 の図と全出力（ログ、把持ごとの CSV、モンタージュ）は `<scratchpad>`/d4/ にある。事前登録は floor_ja.md F7（2026-10-12 22:58）。印：【測】実データで測った、【計】計算、【仮】仮定。
確からしさは 高 / 中 / 低。**「事後」**は、データを見てから選んだ窓や推定量のこと。事前登録の判定には使っていない。

## 問い
F5 の木の立方体では、着地の後にカメラに映るパッドの移動は、エンコーダが予測する移動の 0.11 倍だった（四分位 0.04〜0.52、32 把持）。柔らかい物なら、パッドは物体に入り込むので r は 1 に近づくはずだ。

測る対象は xhaka3456/openarm_pick_strawberry_and_place_on_white_plate2（以下 v2。偽物のイチゴ、F1）の左手首カメラ（640×480、30 fps）。
r = カメラが見たパッドの移動 ÷（エンコーダの移動 × このカメラの px/deg）を、着地の後について測る。
直列ばね模型 r = k_g / (k_g + 4 k_obj r_c²) から k_obj を出す（k_g 140 Nm/rad は A の値の流用【仮】、r_c 0.06〜0.097 m）。

予測は三つ：本物のイチゴ 0.79〜0.95、偽物 0.07〜0.83（k_obj 2〜50 N/mm）、立方体 ≤ 0.09。
v2 で測れたので、旧版の ..._plate（以下 v1）でも別に測った。

## 結論
1. **事前登録どおりの着地の r（A→B5）は未決**【測、中】。
   - **v2**：測った時刻ずれに合わせた整数ずらし s = −2 で、中央値 **0.391**（四分位 −0.030〜0.590、n 71/79、判定 4 での除外 8）。
     - 判定 1（≤ 0.2）と判定 2（≥ 0.5）の間にあり、どちらにも入らない。
     - ずらし −2..+2 では 0.391 / 0.083 / 0.054 / 0.045 / 0.029。0.5 はまたがないので、判定 3 は字義どおりには働かない。
     - ただし 0.2 は s −2 と −1 の間でまたぐ。四分の一コマ早い −2.25 にずらすと 1.26 になる。
   - **v1（再現）**：s −2 で **0.638**（0.143〜2.690、n 32/36、除外 4）、s −1 で 0.172。**−2..+2 の中で 0.5 をまたぐので、判定 3 により未決**。
   - 二つの公開版の値が合わない（0.39 対 0.64）。把持ごとの時刻ずれを使っても、v2 0.335（n 56）、v1 0.592（n 29）。
   - **未決の理由は、推定量の条件の悪さ**。
     - 閉じる段は約 9°/コマ（開きで約 50 px/コマ）なのに、着地の後の進みは中央値 0.37°（開きで約 2 px）しかない。
     - カメラは記録された q より中央値 1.89 コマ先行している（把持ごとの sd 0.44 コマ）。
     - そのため、時刻の当て方がコマの端数だけ違うだけで、速い段の最後が窓に入り、着地後の移動と同じ大きさになる。上の −2.00→−2.25 で 0.39→1.26 になったのが、その測った大きさ。
   - **判定 5（指令と位置のずれで A を、指令の停止で B を決める）は、このデータでは使えない**。グリッパの状態列と指令列は全コマで一致し、速度とトルクの列はすべてゼロ【測、高、51,825 / 24,980 コマ】。A と B はエンコーダから決めた（方法）。
2. **事後の推定量では、両版とも r ≈ 0.55〜0.70 で、時刻ずれにほぼ依らない**【測、中、事後】。ここでは窓の始まりを着地の 2〜5 コマ後にして、着地の過渡を外している。
   - **A+2→Bend**：v2 0.667（0.36〜0.81、n 65）、v1 0.682（0.56〜0.91、n 32）。ずらし −3..0 で v2 0.59〜0.67、v1 0.59〜0.76。+1 では 0.49 / 0.47。
   - **A+5→Bend**：v2 0.581（0.386〜0.772、n 62/77、除外 15）、ずらし −2..+2 で 0.54〜0.65。v1 0.702（0.529〜0.884、n 30/34、除外 4）、同じく 0.43〜0.70。
   - **保持中の回帰**（A+5..Bend の開きの q に対する傾き ÷ 校正の傾き）：v2 0.552（0.474〜0.698、n 74）、ずらし −2..+2 で 0.55〜0.60。v1 0.607（0.470〜0.731、n 36）、0.55〜0.61。
   - **時刻ずれとの関係**：把持ごとの時刻ずれと A+5→Bend の r の順位相関は、v2 +0.13、v1 −0.01。着地の r では v1 +0.45 で、時刻の誤差に引かれていた。
   - **ただし校正に依る**。開端（q −37〜−35）の校正に替えると 0.46〜0.59 になる（v2：A+5 0.481、回帰 0.455〜0.49。v1：0.588、0.46〜0.51）。**0.5 を超えるかどうかは、校正の選び方で変わる**。
3. **予測の帯との関係**【計、中】
   - 事後の中央値 0.55〜0.70 は、本物のイチゴの帯（0.79〜0.95）より下にあり、偽物の帯（0.07〜0.83）の中にあり、同じ窓での立方体（0.05〜0.10）より上にある。
   - 偽物の帯は広いので、その中に入ること自体はほとんど何も言わない。言えるのは、立方体とは違うこと、本物のイチゴの予測より低いことまで。
   - **k_obj**（k_g 140 Nm/rad を流用【仮】、r_c 0.097〜0.06 m）は、保持角の校正で **1.6〜7.9 N/mm**、開端の校正まで含めると 1.6〜11.6 N/mm。
     - 偽物の予測（2〜50）の下端にあたり、本物のイチゴ（0.5〜1）より 2〜10 倍硬い。
     - k_g は xhaka3456 の個体では測っていない。k_obj は k_g に比例して動く。
4. **立方体との比較（事後。個体とカメラが違う）**【測、中、n 9〜32】
   - F5 の木の立方体（padcal.npz、32 把持、開きの傾き −5.14 px/deg、整列のずらし +1）に同じ窓を当てた。A→Bend 0.05（n 32）、A+2→Bend 0.07（n 16）、A+5→Bend 0.10（n 9）。窓の始まり j 2〜8・ずらし 0〜+2 では −0.01〜0.32。
   - 保持中のエンコーダの進みは、立方体（A+2→Bend 中央値 0.39°、トルクの増え +0.30 Nm）とイチゴ（v2 0.37°）でほぼ同じ。それなのに、カメラがその進みについて来るのはイチゴだけ。
   - F5 の 0.11 を式に通すと k_obj は 30〜79 N/mm、整列後の 0.05 なら 71〜185 N/mm。事前登録の「剛体級 ≥ 40 N/mm」と矛盾しない。
   - ただし二つは、個体、カメラ、検出（F5 は縁、ここは穴）、校正、除外の規則がすべて違う。
5. **判定の答え**：事前登録の判定は「未決」。
   - 事後の保持中の r は判定 2 の側（≥ 0.5）に寄る。しかし開端の校正では 0.46〜0.51 にかかり、窓は事後に選んだものなので、「パッドが物体を押し込んでいる」とは言い切らない。
   - **仕組みも分けられない**。保持中のカメラの動きは、物体の弾性・クリープ・滑り（r → 1 の側）とも、伝達系が落ち着く動き（r → 0 の側）との混ざりとも読める。トルクも指令もないので区別できない。
   - **圧縮はモンタージュでは見えず、判定 1 の目視は使えない**。保持中に予測されるパッドの移動は、パッド 1 つあたり約 0.4 px しかない。差分画像では、背景（皿、ほかのイチゴ、机）の動きと物体の輪郭が支配的になる。
   - 確からしさは 中。
6. **何があれば決まるか**
   - (a) 指令列かトルク列。判定 5 をそのまま使える。
   - (b) カメラと関節のハードウェア同期か、120 fps 以上。着地の窓の条件の悪さが消える。
   - (c) 同じ個体・同じカメラで剛体を握った映像。k_g と「r → 0」の対照を同じ系で取れる。
   - (d) ゆっくり閉じる動作。速い段の尾が、着地後の移動より小さくなる。
   - (e) 本物のイチゴ。

## 方法
- **データ**：v2（40 エピソード、51,825 コマ）と v1（20 エピソード、24,980 コマ）から、meta/*、data/*、videos/observation.images.left_wrist/* だけを新しい空のディレクトリに取った。
  - v2 のディレクトリは、同じ日 16:53 の取得ですでに中身があった。head、head_depth、right_wrist の動画も 1 ファイルずつあるが、使っていない。
  - 使った 27 ファイルの大きさは、_files.json の一覧とすべて一致した（27/27）。
  - スクリプトは sim_demos/floor/ に置き、/usr/local/bin/python3（CPython 3.10.8、pyarrow 20.0.0、numpy 1.23.5）を `-I` と nice 10 で動かした。venv には pyarrow がない。
- **グリッパの値**：observation.state の列 14（left_gripper.pos）。
  - 値の最小刻みはちょうど (25/65535 rad) × (0.044/1.0472 m/rad)。つまり Damiao の 16 bit 位置を、openarm_hardware の 0.044 m ↔ 1.0472 rad で換算した値【測、高】。
  - モータの deg に戻す式は q = −値 / (0.044/1.0472) × 180/π。0 が閉で、開は約 −35。
  - 左のグリッパを使うエピソードは、v2 で 21（右だけ 17、どちらも使わない 2）、v1 で 10。カメラが左手首なので、左だけを使った。
- **復号**：ffmpeg で、エピソードごとに from_timestamp から順に復号した（640×480）。
  - **自分の書いたコードに不具合があった**。開始時刻を丸めて書いたため、値が最初のコマの pts を越え、ffmpeg の正確なシークがそのコマを落としていた。結果としてエピソード全体が 1 コマずれる（例：1217/30 → "40.5667"）。
  - 該当は v2 の 6・8・9・19・27・34 と、v1 の 5。シークを四分の一コマ早めて直し、すべて取り直した（explore/seekround.py で確かめた）。
  - 直す前の出力は *_seekbug という名前で残してある。直す前は、v2 の時刻ずれ −2.16（把持ごとの sd 0.61）、着地の r 0.234、v1 は −1.83 と 0.528 だった。
  - ffmpeg 自体の不具合ではないので、課題管理の検索はしていない。
- **パッドの位置**：各パッドの貫通穴を、暗い小さな塊として取った（左のパッドに 1 つで L、右に 2 つで Ru・Rl）。
  - 位置はコントラストで重みをつけた重心で、画素より細かく出す。穴はパッドに固定されていて、隣に何が写るかに左右されない。
  - 割り当ては、q から決めた事前位置で行う。静止コマで事前位置を当て直し、±6 px で割り当て直した。検出率は 3 穴・両版で 97.7〜99.4%。
  - 測る量は開き G = Ru − L（Ru が隠れたら Rl − L）。差を取ることで、カメラと手に共通の動きが消える。
  - 事前登録は「パッドの縁」を追うとしていたが、穴を主にした。縁は副として取ってあるが、物体の色に引かれる。
- **事象**（エンコーダだけで決める）：開いた状態（q < −28°）からの閉じる段を一つの把持とした。
  - **A**：速い段の終わり。s0 から 5° 以上進んだ後、2 歩続けて 1.333°/コマ（40°/s、F5 の閾値）未満になる点。
  - **B5**：最初の 5 コマ平坦（|Δq| < 0.05°）の始まり。
  - **Bend**：保持の終わりの 2 コマ前。保持の終わりは、離したときか、保持中に 1°/コマを超えて跳んだとき。
  - 保持が 15 コマ未満は short、着地が −8° より閉じていれば empty として除いた。保持中の跳び（握り直しか滑り）があれば、窓をその手前で切った。握り直しは着地に数えない。
- **時刻**：各閉じる段で、穴の x と q がそれぞれ段の中点を横切る時刻を、コマの端数まで出して差を取った（カメラ − エンコーダ）。
  - 全穴・全把持の中央値で、整数のずらし s を決める（カメラのコマ番号 = エンコーダのコマ番号 + s）。
- **校正**（このカメラで取り直した。A の +2.63 / −2.51 は使っていない）
  - (i) 開端：q < −30° で、q が同じ値のまま静止している 15 コマ以上の塊を使う。
  - (ii) 保持角：保持ごとに A+5 の q と、ずらし後のカメラの x を並べ、ロバストな直線を引く。r は保持角で測るので、(ii) を主にした。
  - (iii) 二つの直線を、互いの端と閉端で評価して直線性を見る。
- **r と除外**：r = カメラの開きの変化 ÷ (Δq × 開きの傾き)。
  - 開きの傾きは穴の傾きの差で、保持角では Ru−L が −5.84、Rl−L が −5.64 px/deg。
  - 判定 4 として、予測される開きの変化が、その保持の片縁のゆらぎの 3 倍に満たない把持を除いた（中央値のゆらぎ 0.23 px なら、Δq が約 0.12° 未満のもの）。
  - 変種として、開きのゆらぎを使った除外も出した。ゆらぎは、保持中に q が一定のまま 10 コマ以上続く区間での、コマごとの標準偏差。
- **着地の列**：カメラの着地は、開きが 15 px 以上閉じた後、2 コマ続けて 1.5 px/コマ以内に収まる最初のコマとした。A との差を数える。
- **事後の推定量**
  - 窓 [A+j, Bend]（j は 0〜8、Bend − (A+j) ≥ 10 コマ）。
  - 保持中の回帰。
  - 端数のずらし（カメラ列を線形補間）。
  - 把持ごとの時刻ずれとの順位相関。
  - 赤の面積比の変化（物体の動きの代わり）。
  - 立方体の対照は、F5 の padcal.npz を読み、その傾き −5.14 px/deg と整列のずらし +1 で同じ窓を当てた。
- **k_obj** = k_g (1 − r) / (4 r r_c²)。r が (0, 1) の外なら定義しない。

## 仮定と確からしさ
- **事前登録からの逸脱**
  1. 指令列がないので、A と B はエンコーダから決めた（判定 5 は使えない）。
  2. 校正は保持角のものを主にした（開端も併記した）。
  3. パッドの縁ではなく穴を追った。
  4. python は venv ではなく /usr/local/bin/python3 を使った（調整役の指示による）。
  5. v2 のディレクトリには、先に取得した中身があった（大きさは確認済み）。
  6. 復号の 1 コマずれを見つけて直し、全部を取り直した（直す前の結果は *_seekbug）。
  7. 使えたのは左グリッパのエピソード（21/40、10/20）だけ。
  8. 事後の窓と立方体との比較は、事前登録になかった。
- **k_g 140 Nm/rad と r_c 0.06〜0.097 m は個体 A の値**【仮、低〜中】。xhaka3456 の個体では測っていない。k_obj は k_g に比例する。比 n = 1 とした。
- **時刻**【測、高】：カメラが記録された q より約 1.9 コマ（v1 は 1.7）先行している。原因（記録の作り方か、カメラの露光時刻か）は調べていない。F5（+1）と符号が逆。
- **エンコーダの値の重複**：動いている間に 17.4% のコマで値が繰り返される。状態の更新がコマに追いついていない可能性があり、把持ごとの時刻のばらつき（v1 で sd 1.01）の一因かもしれない。確かめていない。
- **保持中の動きの仕組み**は分けていない。物体の弾性・クリープ・滑り・回転は r を 1 の側へ、伝達系の落ち着きは 0 の側へ寄せる。
  - 赤の面積比の変化（物体の動きの代わり）と r の相関は、v2 −0.20、v1 +0.23 で符号がそろわず、何も言えない。
- **立方体との比較は、同じ系での対照ではない**。個体 A、別のカメラ、縁の検出、F5 の校正（開きの傾き −5.14 px/deg）、別の除外規則を使っている。n も窓が遅くなると 9 まで減る。
- **握り直し**（v2 16、v1 13）は着地に数えず、r も出していない。保持中に跳んだ 6 保持（各版）は、窓をその手前で切った。
- **この課題では文献を検索していない**。F7 の「先行」段落（2026-10-12 の検索）を超える主張はしない。
- **確からしさ**：事前登録の着地の r は「未決」（高）。事後の保持中の r 0.55〜0.70 は 中。「0.5 を超える」は 低〜中（校正に依る）。k_obj 1.6〜11.6 N/mm は 低〜中（k_g の流用に比例して動く）。
